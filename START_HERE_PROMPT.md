# Первый запуск Antigravity: полный аудит OkuTutor и подготовка MVP-карты

Скопируй этот запрос в Antigravity, открыв корень монорепозитория `okututor`.

---

Работай как главный инженерный архитектор и руководитель аудита. Твоя цель — установить фактическое состояние OkuTutor и подготовить точный MVP-план реального запуска.

**На этом проходе режим строго READ-ONLY. Не редактируй бизнес-код, конфигурации, миграции, Docker и workflow. Разрешено создавать/обновлять только файлы аудита в `docs/` после согласования отчётов. Не делай git reset, checkout с потерей изменений, clean, force push, deployment и другие destructive-действия.**

## 0. Подготовка

- Прочитай `AGENTS.md`, `PROJECT_CONTEXT.md`, `docs/PROJECT_FACTS.md`, все правила `.agents/rules/`.
- Проверь `git status`, активную ветку, последний commit и структуру репозитория.
- Зафиксируй дату, branch и commit SHA аудита.
- Не выводи секреты из `.env`, CI secrets или config. Проверяй только наличие placeholder/default и риск их применения.

## 1. Оркестрация аудита

Используй `/swarm` или отдельные custom subagents. Назначь независимые направления:

1. `product-auditor`: страницы, user journeys, UI-компоненты, меню, кнопки, состояния loading/empty/error, доступность и продуктовый MVP.
2. `frontend-engineer` в режиме read-only: роуты, layouts, компоненты, API-клиенты, stores, query keys, i18n, формы, валидация, ошибки, тесты и неиспользуемые экраны.
3. `backend-auditor`: контроллеры, endpoints, сервисы, сущности, права доступа, валидация, rate limits, фоновые процессы и тесты.
4. `database-specialist` в режиме read-only: все Flyway migrations, фактическая схема, индексы, FK, constraints, seed data, потенциально legacy-таблицы. Ничего не менять.
5. `security-auditor`: auth lifecycle, JWT/refresh, OAuth, CSRF/CORS, IDOR/BOLA, authorization, PII, file uploads, rate limits, secret defaults, admin boundaries.
6. `release-engineer` в режиме read-only: Dockerfiles, compose, CI, environment variables, health checks, deployment assumptions, storage persistence, backups, monitoring and rollback.
7. Главный агент выступает `verifier`: проверяет доказательства, устраняет разночтения, ищет пропущенные ссылки и не принимает голословные выводы.

У каждого агента — непересекающаяся область чтения. На данном этапе никто не меняет исходный код.

## 2. Инвентаризация UI

Найди все маршруты и заполни таблицу для каждой страницы:
- route и доступность (public/auth/role);
- фактический page component и layout;
- дочерние UI-компоненты;
- все пользовательские действия и вызываемые handlers;
- API endpoints и payloads;
- состояния loading, empty, error, success;
- валидация на frontend и backend;
- роли и ownership checks;
- тесты, подтверждающие сценарий;
- статус: `CONFIRMED_IN_CODE`, `ROUTE_ONLY`, `DOC_ONLY`, `NEEDS_E2E`, `LEGACY`, `NOT_FOUND_IN_AUDIT`, `DECISION_REQUIRED`.

Ищи не только страницы, но и маршруты, drawer/modal/dialog, формы, табы, фильтры, dropdowns, toasts, mobile nav, admin actions, SEO metadata, sitemap, 404/403, legal pages.

Не называй компонент реализованным только потому, что он импортирован. Проследи обработчик до API и backend-сервиса.

## 3. Сквозные MVP-сценарии

Проверь цепочки от начала до конца:

A. Посетитель открывает главную → ищет по предмету/городу/тексту → применяет фильтры → видит результаты → открывает опубликованную анкету → отправляет запрос → получает подтверждение.

B. Пользователь регистрируется/входит → создаёт или редактирует TutorProfile → сохраняет черновик (если реализовано) → отправляет на модерацию → видит статус и ошибки валидации.

C. Администратор входит → видит очередь модерации → открывает анкету → одобряет/отклоняет с причиной → публичный каталог отражает новый статус → автор получает понятный результат.

D. Репетитор видит входящие заявки; ученик видит отправленные; статусы и права доступа корректны. Отдельно проверь пользователя, который и ищет репетиторов, и имеет собственную анкету.

E. Пользователь обновляет профиль/контакты, меняет пароль, завершает сессию, запрашивает удаление аккаунта (если путь доступен).

F. Администратор блокирует пользователя; заблокированный пользователь не может продолжать доступ только за счёт старого access token.

Если часть цепочки не реализована, отметь точный разрыв — не заменяй его предположением.

## 4. Границы MVP

Предложи на запуск только минимум, необходимый для работающего маркетплейса:
- публичная главная;
- каталог и базовый поиск/фильтры;
- публичная карточка анкеты;
- регистрация/вход и восстановление доступа;
- создание/редактирование/отправка анкеты;
- модерация анкеты;
- рабочая отправка и просмотр заявок/контакта;
- профиль и базовые настройки пользователя;
- базовая админ-панель (модерация, блокировка, минимальная статистика);
- стабильный production deployment, база, media storage, email, logs, health, backups, security.

Для каждой функции выбери `MUST_HAVE`, `SHOULD_HAVE`, `POST_MVP`, `REMOVE_FROM_PRIMARY_FLOW`, `BLOCKER`. Обоснуй выбор через пользовательскую ценность и риск запуска.

Отдельно классифицируй отзывы, избранное, чат в реальном времени, расписание/уроки, видео, курсы, прогресс, отчёты, расширенную аналитику, SEO-admin, support tickets и дополнительные роли. Не удаляй автоматически.

## 5. Проверки и доказательства

- Запусти только безопасные команды анализа: tree/find/grep, tests, lint, build, если они не изменяют tracked files и не обращаются к production.
- Для каждой команды зафиксируй точную команду и результат.
- Не утверждай, что test suite passed, если не запускал его.
- Проверь Docker build для backend и frontend, не поднимая production-сервисы и не публикуя образы. Если не хватает файлов/переменных — сообщи.
- Проверь, что workflow triggers учитывают изменяемые общие файлы.

## 6. Deliverables

Обнови только документы:

1. `docs/PROJECT_FACTS.md` — фактический стек, каталоги и ключевые паттерны с путями.
2. `docs/REPOSITORY_AUDIT.md` — findings по приоритету P0/P1/P2/P3, evidence, impact, remediation, verification.
3. `docs/MVP_FUNCTIONAL_MAP.md` — полный актуальный реестр маршрутов, страниц, UI-компонентов и действий с endpoint, ролями, состояниями и статусами.
4. `docs/API_CONTRACTS.md` — реальные endpoint/DTO и несогласованности frontend/backend.
5. `docs/MVP_RELEASE_GATES.md` — checklist, блокеры и критерии go/no-go.
6. `docs/AUDIT_TASK_BACKLOG.md` — атомарные задачи с зависимостями и критериями приемки.

Для каждой находки дай ссылку на файл/символ и строку или фрагмент кода. Отделяй подтверждённый факт от предположения.
